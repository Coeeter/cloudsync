# Cloudsync serverless platform research

Researched 2026-10-11 against official documentation and current package metadata. Architecture evaluation only; no infrastructure or application changes. Prices are USD before taxes. AWS examples below are explicitly US regional illustrations, not verified Singapore quotes.

## Recommendation

For this existing app, prefer **AWS Lambda + a small Neon Postgres database**, retaining S3 and CloudFront, with explicit SQS jobs and a separate Lambda container for native previews. Retaining Postgres avoids rebuilding catalog concurrency, SQL queries, migrations and job state solely to save a small monthly database bill. Evaluate **SST** first for infrastructure and TanStack hosting. A Bun container with Lambda Web Adapter is the fallback if converting the web application to Node is more invasive than expected. SST's high-level TanStack component and a Bun container are separate hosting approaches, not an automatically compatible combination.

DynamoDB is reasonable for a newly designed application with known key access patterns; it is a substantial migration here. Workers + D1 is a credible alternative for the web/API layer, but still requires a different runtime/database implementation and a native compute service. It does not remove the preview and archive problem.

Local evidence: `apps/cloud/vite.config.ts` uses Nitro's Bun preset; package versions are TanStack Start 1.168.58, Nitro 3.0.260903-beta, Effect/platform-bun 4.0.0-rc.117 and Drizzle 0.45.3. Database schema uses PostgreSQL enums and JSONB. Catalog and archives call `pg_advisory_xact_lock`. These are concrete migration boundaries, not assumptions about framework support. Parent's read-only production audit reports approximately 74,723 entries, 157.89 GB of objects, largest file 78.84 MB, and archive output up to 374.72 MB in retained records; current file sizes are samples, not product limits.

## Runtime and database choices

| Choice | Verified capability / limit | Implication for Cloudsync |
|---|---|---|
| Workers | 128 MB per isolate; Free 10 ms CPU, Paid default 30 seconds configurable up to 5 minutes CPU; HTTP wall time can continue while client connected; `waitUntil` only 30 seconds after response/disconnect. `child_process` is an importable **nonfunctional stub**. | TanStack SSR can run; Bun APIs and ffmpeg/Poppler/img2webp processes cannot run in ordinary Workers. Streaming must avoid buffering. CPU limit is different from HTTP wall time. |
| D1 | SQLite semantics; Free database maximum 500 MB, Paid 10 GB (cannot increase); single threaded per database, 30-second SQL query/batch duration. | SQL relationships remain possible, but Postgres schema, driver, migrations, advisory locks and concurrent mutation logic must change. It is not serverless Postgres. |
| Standard on-demand Lambda | 15-minute invocation limit; 128–10,240 MB memory; roughly one vCPU at 1,769 MB; `/tmp` 512–10,240 MB; image up to 10 GB; synchronous response 6 MB, streamed response up to 200 MB then bandwidth capped after first 6 MB. | Native binaries fit in a container; large files need direct S3 uploads/downloads. Current 374 MB archives already exceed Lambda streamed response maximum: generate asynchronously into S3. Existing two-hour archive timeout cannot be preserved by one ordinary Lambda invocation. |
| DynamoDB | 400 KB item limit including names; transactions up to 100 distinct items / 4 MB, with conditional expressions available. No native relational joins; key/index access patterns must be designed. | Keep file objects in S3; do not put arbitrarily growing archive manifests in one item. Directory uniqueness, rename/delete invariants, search and transaction boundaries need an explicit data-model redesign. |
| Neon | Actual Postgres, scales to zero after five idle minutes on Free/Launch; Free 100 CU-hours/project, **1 GB** storage/project, 5 GB egress/project. | Lowest migration risk, but a permanently polling worker prevents the desired idle behavior. Replace polling with SQS and use an appropriate pooled connection configuration. |
| Aurora DSQL | Postgres-compatible SQL/wire protocol with joins and ACID transactions, but optimistic concurrency and serialization retries rather than pessimistic locking; separate DDL/DML transactions; up to 3,000 modified rows/transaction; no temporary tables/triggers/PLpgSQL. | A plausible AWS-native candidate, but advisory-lock coordination and migration execution need redesign/verification. **Foreign keys are now supported** (released August 27, 2026); older advice saying otherwise is stale. |

## Framework and deployment tooling

Cloudflare officially supports TanStack Start using its Vite plugin. Nitro also documents `cloudflare_module` and `aws_lambda` output presets. SST's current `sst.aws.TanStackStart` documentation requires a Lambda Nitro target (spelled `aws-lambda` there). The spelling and integration should be verified against Cloudsync's installed **Nitro 3 beta**, rather than copying a snippet across versions. The current Bun preset output is not itself a Lambda event handler. [Cloudflare Vite](https://developers.cloudflare.com/workers/local-development/vite-plugin/), [Nitro AWS](https://nitro.build/deploy/providers/aws), [Nitro Cloudflare](https://nitro.build/deploy/providers/cloudflare), [SST TanStackStart](https://sst.dev/docs/component/aws/tan-stack-start/).

Bun's official Lambda guide uses a Bun Debian container with **AWS Lambda Web Adapter**, so retaining Bun is feasible. A background SQS processor needs an event handler/runtime integration rather than assuming the HTTP adapter will execute the existing forever-running worker loop. Images must obey Lambda's runtime API and writable `/tmp` constraints. [Bun guide](https://bun.com/guides/deployment/aws-lambda), [AWS container requirements](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html), [custom runtimes](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-custom.html).

Current npm `latest` checked read-only: SST **4.17.2**, Serverless Framework **4.43.0**. SST uses Pulumi's deployment engine/providers and bridged Terraform providers; its official description does **not** call it OpenTofu. Its open-source CLI is free, optional Console separate, no Pulumi account required. This is different from old SST v2/CDK advice. Serverless Framework v4 remains viable and free for organizations at or below $2 million annual revenue, but requires authentication; above threshold license rules apply. Serverless v3 is no longer maintained. AWS CDK v2 is the AWS-native TypeScript/CloudFormation alternative, with more assembly needed for the app integration. There is no documented universal “current standard”; **SST is the most direct fit for this TypeScript/TanStack project**, while CDK is reasonable if AWS-native tooling is preferred. [SST architecture/licensing](https://sst.dev/docs/), [Serverless pricing](https://www.serverless.com/pricing), [Serverless v4](https://www.serverless.com/framework/docs/guides/upgrading-v4), [AWS CDK](https://docs.aws.amazon.com/cdk/v2/guide/home.html), [SST npm metadata](https://registry.npmjs.org/sst/latest), [Serverless npm metadata](https://registry.npmjs.org/serverless/latest).

## Preview and archive event design

Recommended flow: direct signed upload to S3 → verified application upload finalization → enqueue missing preview jobs in SQS → native preview Lambda → write previews to S3 → conditionally mark job complete. Preserve desktop-generated preview verification. A raw S3 ObjectCreated event can arrive before metadata finalization or before desktop previews are recorded; it must not blindly generate another preview.

S3 events can be an additional ingestion/reconciliation trigger, but delivery is at least once, may be duplicated, and is not ordered. Native S3 notifications support standard SQS; FIFO needs EventBridge. Filter to original-object prefixes and exclude generated preview/archive prefixes to prevent feedback loops. This filtering does not prove the application metadata is ready. [S3 event semantics/destinations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html), [key filters](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-filtering.html).

Use a job identity incorporating entry/object version and processing version; conditionally claim with an expiring lease, write deterministic output, and conditionally complete against the current generation. A duplicate should observe completion; a crash must permit reclaiming. Enforce retry/DLQ behavior and concurrency bounds, and return partial batch failures. AWS recommends SQS visibility at least six times function timeout plus batch window. A unique SQL record/conditional update can provide this without migrating the whole app to DynamoDB. [Lambda SQS configuration](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html).

Archives should be requested as jobs, stream S3 inputs into multipart S3 archive output, and return a signed download when ready. Bound job duration/output explicitly or retain a container task/VPS path for jobs beyond ordinary Lambda's runtime limits. Benchmark worst supported formats and archives before selecting memory, `/tmp` and timeout.

## Low-activity cost model

| Component | Published rate / illustrative result |
|---|---|
| Workers Paid + D1 within inclusion | $5/month minimum includes 10 million Worker requests and 30 million CPU-ms. D1 includes 25 billion rows read, 50 million written, 5 GB storage/month. Extra D1: $0.001/million rows read, $1/million writes, $0.75/GB-month. Free exists, but hard daily/runtime/database caps can fail the app. |
| Standard Lambda illustrative US x86 rate | $0.20/million requests, $0.0000166667/GB-second; published monthly free allowance 1 million requests and 400,000 GB-seconds, shared with eligible account usage. 10,000 web invocations at 512 MB × 0.2 s plus 1,000 jobs at 2 GB × 10 s = **21,000 GB-seconds**, approximately **$0.35 compute before free allowance**, not including cold-start initialization, retries, queue, logs, image storage, extra `/tmp` or transfer. |
| Neon Launch | No monthly minimum; $0.106/CU-hour + $0.35/GB-month, with separate retained-history/snapshot charges. 0.25 CU × 20 active hours + 0.5 GB = **$0.705/month** before history. Always-active 0.25 CU × 730 h = **$19.345 compute**, demonstrating why polling destroys savings. Free may suffice if measured database fits its allowances. |
| DynamoDB illustrative US East | $0.625/million 1 KB write units and $0.125/million strongly consistent ≤4 KB read units. 100,000 of each = **$0.075**, before extra indexes/transaction units/backups; 25 GB Standard storage free allowance. Low cost does not justify a correctness-heavy rewrite automatically. |
| Aurora DSQL illustrative US Ohio | First 100,000 DPUs and 1 GB storage/month included. Published US example $8/million DPUs and $0.33/GB-month. DPUs depend on query/maintenance work, not a direct count of user requests. Verify Singapore availability/rates and app compatibility before adopting. |

Primary pricing: [Workers](https://developers.cloudflare.com/workers/platform/pricing/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [Lambda](https://aws.amazon.com/lambda/pricing/), [Neon current official source](https://github.com/neondatabase/website/blob/main/content/docs/introduction/plans.md), [DynamoDB](https://aws.amazon.com/dynamodb/pricing/), [Aurora DSQL](https://aws.amazon.com/rds/aurora/dsql/pricing/).

These calculations are workload assumptions, not production bill forecasts. Original S3/CloudFront storage and delivery already exist and remain billed; the 157.89 GB object inventory is **not** the metadata database size. Thumbnail/ZIP outputs add storage and requests. Choose standard on-demand SQS/Lambda without provisioned capacity or a NAT gateway for this low-activity design where possible. Measure actual DB size, request counts, job duration/memory, cold starts, retained history and regions before claiming total savings. A small shared VPS may still be simpler if this is only to save a few dollars and other services still need it.

Additional production timing evidence from parent: 71,307 completed/error-free preview records have mean `(updated_at - locked_at)` 1.11 seconds, p95 1.99 seconds, maximum 76.30 seconds; four archives average 14.75 seconds, maximum 24.78 seconds. These are historical retained records, **not monthly workload**. Heartbeats can bias lock-based timing, and VPS runtime does not establish Lambda duration/memory. As a rough dimensional check, 71,307 × 1.11 seconds × 1 GiB is about 79,151 GB-seconds across those records; use only to justify a benchmark, not a billing forecast.
